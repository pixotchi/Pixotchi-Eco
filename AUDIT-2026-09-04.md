### PX-01 — Quest finalize destroys the reward and the app celebrates it

**Severity:** Critical · **Status:** PROVEN
**Files:** `components/building-details/FarmerHousePanel.tsx:210`, `v22/src/libs/LibQuest.sol:136`

**Evidence**

The contract gives a 256-block (~8.5 min on Base) window between `questCommit` and `questFinalize`. Past it, `finalizeQuest` does **not revert** — it resets the quest and returns a zero reward:

```solidity
// v22/src/libs/LibQuest.sol:136
if (block.number > quest.pseudoRndBlock + 256) {
    resetQuest(landId, farmerSlotId);
    emit QuestReset(landId, farmerSlotId, msg.sender);
    return (false, RewardType.SEED, 0);   // <-- no revert; receipt is "success"
}
```

The app treats any successful receipt as a win:

```tsx
// components/building-details/FarmerHousePanel.tsx:210
onSuccess={async () => {
  await handleSuccess({ slotIndex: idx, awaitUncommitted: true });
  toast.success('Loot bag opened!');   // <-- unconditional
}}
```

**Reproduction**

Committed a quest on land #712, let the window lapse, then clicked "Open now".

```
Onchain state read before finalize:
  slot 0: pseudoRndBlock=50843746  -> deadline block 50844002
  current block 50845408  ->  EXPIRED, 1406 blocks late (~46.9 min)

Finalize tx: 0x4bc85e157fa9c2768256754d10a7bd693ef9d168edab7cd74e461b998603580a
  status   : success
  gasUsed  : 47474          (the cheap reset path — no reward transfer)
  events   : QuestReset     (NOT QuestFinalized)
```

Throughout those 47 minutes the slot displayed **"Committed · Loot bag ready · Open now"** with no countdown, no warning, and no disabled state. After the click the UI reported success.

**Root cause**

Two gaps: the Committed state has no deadline awareness at all, and `onSuccess` never decodes the contract's `success` return value or inspects the receipt logs.

**Impact**

Players silently lose Farmer House quest rewards — the core land loop — and are told they received them. Any interruption longer than ~8 minutes triggers it: a phone call, a backgrounded Mini App, a slow wallet confirmation, a congested block.

**Fix (app-side)**

1. In the `Committed` branch, render a live countdown derived from `pseudoRndBlock + 256`. Disable "Open now" once expired and replace it with an explicit *"Reward expired — reset this slot to start a new quest"* action.
2. In `onSuccess`, parse the receipt logs. Toast success only when `QuestFinalized` is present; on `QuestReset`, show a truthful expiry message instead.
3. Consider surfacing the deadline in the `Ready to commit` state too, so players know a timer starts when they commit.

### PX-02 — Every upgrade countdown over 24 hours is wrong

**Severity:** High · **Status:** PROVEN
**File:** `lib/utils.ts:457` — `calculateTimeLeft()`

**Evidence**

`intervalToDuration` returns `{ years, months, days, hours, minutes, seconds }`. The function reads only `hours` and `minutes` and discards `days` entirely:

```ts
const duration = intervalToDuration({ start: 0, end: secondsLeft * 1000 });
const h = duration.hours || 0;
const m = duration.minutes || 0;
if (h > 0) return `${h}h ${m}m`;
else       return `${m}m`;
```

Executed against the real `date-fns` with the real function body:

| True remaining | UI shows |
|---|---|
| 23h 59m | `23h 59m` ✅ |
| **24 hours** | **`0m`** ❌ |
| **26 hours** | **`2h 0m`** ❌ |
| **48 hours** | **`0m`** ❌ |
| **96 hours** | **`0m`** ❌ |
| **30 days** | **`0m`** ❌ |

**Impact**

Every long building upgrade — including the 24h Marketplace build — tells the player it is finishing imminently, then keeps saying `0m` for a full day. Compounds with **PX-09**: the speed-up that would resolve the wait is hidden at exactly the same time.

**Fix**

```ts
const d = duration.days || 0;
const h = duration.hours || 0;
const m = duration.minutes || 0;
if (d > 0) return `${d}d ${h}h`;
if (h > 0) return `${h}h ${m}m`;
return `${m}m`;
```

Clamp or fold `months`/`years` too if any timer can exceed 30 days. One helper backs several panels, so this fixes all of them at once.

Adjacent: `calculateUpgradeProgress` (same file, line ~447) divides by `totalBlocks` with no zero guard.

### PX-03 — `/api/rpc` is an unmetered public Base node billed to your provider keys

**Severity:** High · **Status:** PROVEN
**Files:** `app/api/rpc/route.ts:302`, `proxy.ts:78`

**Evidence**

The only cross-origin guard is `sec-fetch-site`, which **only browsers send**. Any non-browser client that sets an `Origin` header satisfies the allowlist.

```console
$ curl -s -X POST http://localhost:3100/api/rpc \
    -H 'content-type: application/json' \
    -H 'Origin: https://mini.pixotchi.tech' \
    -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
200  {"id":1,"jsonrpc":"2.0","result":"0x307cf9a"}
```

No rate limiting whatsoever:

```console
$ for i in $(seq 1 60); do curl -s -o /dev/null -w "%{http_code}\n" ... ; done | sort | uniq -c
     60 200        # in 10 seconds
```

(Tested against the **production** build, `next start`, `NODE_ENV=production`.)

Two aggravating factors, both confirmed:

**(a) The `eth_getLogs` range guard only inspects hex block numbers.** Named tags sail through:

```console
{"fromBlock":"0x0","toBlock":"latest"}        -> HTTP 200
{"fromBlock":"earliest","toBlock":"latest"}   -> HTTP 200
```

**(b)** Verification confirmed that five such requests trip the **shared server-side circuit breaker**, after which legitimate arcade log reads fail for ~45s for *every* user on that instance. So this is a denial-of-service vector, not just a cost one.

Minor: `web3_clientVersion` is allowed and leaks upstream node identity (`reth/v2.3.0-9384bc5/.../base/v1.2.0`).

**What does work** (do not change): the method allowlist correctly rejects `eth_sendRawTransaction`, `debug_traceTransaction` and `trace_block` with `-32601`, and batch JSON-RPC arrays are refused with 400.

**Fix**

1. Require the chat session cookie (or a signed short-lived token) on `/api/rpc`, exactly as `proxy.ts` already does for `/api/chat/*`.
2. Apply `enforceRateLimit` per IP **and** per address. The helper already exists in `lib/request-rate-limit.ts` and demonstrably works — 40 rapid calls to a 30/min bridge endpoint produced exactly 30 × 200 then 10 × 429.
3. Resolve named block tags to concrete numbers **before** the range-length check.
4. Drop `web3_clientVersion` from the allowlist.

### PX-04 — Mission proof enforcement is dead code

**Severity:** High · **Status:** PROVEN
**File:** `app/api/gamification/missions/route.ts:231`

**Evidence**

Twelve tasks are declared in `TASKS_REQUIRING_PROOF` (`s1_make_swap`, `s1_stake_seed`, `s1_claim_stake`, `s1_place_order`, `s3_apply_resources`, `s3_send_quest`, `s3_claim_production`, `s3_play_casino_game`, `s4_buy10_elements`, `s4_buy_shield`, `s4_collect_star`, `s4_play_arcade`).

The branch that should reject them has **no `return`**:

```ts
if (TASKS_REQUIRING_PROOF.has(missionTaskId) && !proofValid && !proof?.txHash) {
    console.warn(`Task ${missionTaskId} requires proof but none provided - allowing anyway…`);
}
// falls straight through
const updated = await markMissionTask(address, missionTaskId, proof, safeCount);
```

Gamification is **live** in this environment (`GAMIFICATION_DISABLED=false`; the API returns real mission days for real addresses).

**Impact**

Any signed-in wallet can self-credit all 12 onchain tasks with empty POSTs, earning up to 100 Rocks/day toward the monthly leaderboard that pays ETH. The public Rocks leaderboard is fully gameable.

**Related (F070, CONFIRMED):** `taskId` is cast (`taskId as GmTaskId`), not validated, and is interpolated into a Redis key name. An authenticated user can therefore write an unbounded number of permanent Redis keys with attacker-chosen names and arbitrary JSON bodies — no validation, no TTL, no rate limit.

**Fix**

```ts
if (TASKS_REQUIRING_PROOF.has(missionTaskId) && !proofValid) {
  return NextResponse.json({ error: 'Onchain proof required for this task.' }, { status: 403 });
}
```

Validate `taskId` against the `GmTaskId` union **before** it reaches a key name. If smart-wallet proof extraction really is unreliable, gate the exception on the smart-wallet surface specifically rather than disabling proof for everyone.

### PX-05 — A confirmed transaction left the UI stale and silently dropped the mission credit

**Severity:** High · **Status:** PROVEN
**Files:** `components/building-details/FarmerHousePanel.tsx:253`, `lib/mission-tracking.ts:214`

**Evidence**

Clicked **Start** on a quest. The transaction landed:

```
0x9461e4f13d3c0385d4b336139096685d376d55e070307a6d909d0432e499ba55  — status: success
```

Minutes later the panel still read **"Slot 1 · Available · Start"**, and the missions API still reported `s3.sendQuest: false`.

Two independent defects converge:

**(a) The success poll is shorter than block time.** `handleSuccess` polls for the expected state transition **6 × 500 ms = 3 seconds**, then gives up silently:

```ts
for (let i = 0; i < 6; i++) {
  await new Promise((r) => setTimeout(r, 500));
  ...
  if (opts.awaitInProgress && st === 'In progress') break;
}
await fetchSlots();   // may still be stale
```

Base blocks are ~2s and the read path adds latency, so a slot that is genuinely busy keeps rendering an enabled **Start** button. A player can click again and pay gas on a revert.

**(b) Mission credit is gated on the *chat* session, which had silently expired.**

```console
GET  /api/chat/auth/session      -> 401 {"error":"Authentication required for public chat."}
POST /api/gamification/missions  -> 401 {"error":"Authentication required."}
```

The app was otherwise fully functional — wallet connected, transactions signing and landing. Nothing surfaced the dead session.

Recovery exists but is surface-gated:

```ts
// lib/mission-tracking.ts:214
function canRecoverBaseMissionAuth(): boolean {
  const surface = sessionStorageManager.getAuthSurface();
  return surface === "base" || surface === "test";
}
```

**Privy web and the Farcaster Mini App — the two surfaces real players use — have no recovery path at all.** Failed payloads queue in the outbox, retry on `online`/`visibilitychange`, keep 401-ing, and are discarded after `MISSION_OUTBOX_MAX_AGE_MS` (24h).

**Impact**

Players complete daily missions and earn nothing, with no error shown. Rocks feed the monthly ETH leaderboard, so this is an economic loss, not a cosmetic one.

**Fix**

1. Replace the 3s poll with invalidation keyed on the receipt block, or extend it with backoff; disable the action while the slot is known-busy.
2. Extend session recovery to the `privy` and `miniapp` surfaces (or make gamification auth independent of chat auth — the coupling itself is questionable).
3. Surface a visible "progress not saved — reconnect" state rather than failing silently. `MISSION_TRACKING_EVENT` already emits `status: "error"`; nothing renders it.

### PX-06 — The login screen ships ~2 MB of JavaScript

**Severity:** High · **Status:** PROVEN
**File:** `app/providers.tsx:655`

**Evidence**

Measured on a real `next build` + `next start`, **before any wallet connects**:

```
Production login screen — first load
  JS      1,987 KB compressed   (7,352 KB decoded, 59 chunks)
  Fonts     121 KB
  CSS        36 KB
  Total  ~2,145 KB

Largest single chunk: 620 KB gz / 2,722 KB raw
  -> 5,020 occurrences of "solana", 944 of "privy"
```

`<PrivyProvider>` wraps the entire tree unconditionally, even though the auth surface is resolved **synchronously on the first client render**:

```tsx
const [authSurface] = useState<AuthSurface>(() =>
  typeof window === 'undefined' ? 'privy' : resolvePreferredAuthSurface({...})

...
<PaymasterProvider>
  <PrivyProvider appId={privyAppId} config={privyConfig}>   {/* always mounted */}
```

**Related, both CONFIRMED:**
- **F172** — `@solana/web3.js` v1 reaches the first-load graph through a *static* `@farcaster/miniapp-sdk` import, defeating the codebase's own dynamic-import mitigation.
- Two copies of `@solana/kit` (6.10.0 + 5.5.1) reach the client bundle.

**Impact**

This is the single largest cold-start cost for Farcaster Mini App players, who are the primary acquisition channel and are typically on mobile.

Branch on the already-resolved surface and `next/dynamic` the Privy tower so only `privy` / `privysolana` load it. Pin `@solana/kit` (it is the only unpinned dependency in an otherwise pinned manifest) to dedupe the two copies.

### PX-07 — Under RPC failure the app reports "Balance: 0" as fact

**Severity:** High · **Status:** PROVEN
**Files:** `components/item-details-panel.tsx:128`, `components/tabs/mint-tab.tsx`

**Evidence**

Forced `/api/rpc` to return 503 from the client, then used the app normally. The Mint tab rendered:

```
Price      20 0x546D...adc7            <- token symbol lookup failed, raw address shown
Not enough 0x546D...adc7. Balance: 0 • Required: 20
                                   ^ wallet actually holds 3.51 SEED
```

**No toast, no retry affordance, no degraded-state indicator.** Seven RPC calls failed silently.

The pattern is systemic:

```ts
} catch (error) {
  console.error("Failed to fetch SEED balance:", error);
  setUserSeedBalance(BigInt(0));      // <- "unknown" collapses to "zero"
}
```

Same shape at `item-details-panel.tsx:154` (allowance → 0) and `:277` (fence quote → 0).

**Impact**

During a provider incident, players are told they hold nothing and are blocked from legitimate actions by a false "Insufficient" verdict. This is also actively alarming — a user seeing 0 SEED reasonably concludes their funds are gone.

**Fix**

Distinguish *unknown* from *zero* throughout. Model these as `bigint | null`; render `—` with a retry control when null; never let a null balance drive an "Insufficient" verdict or a disabled state that claims a reason it does not know.

### F085 — Blackjack randomness is grindable

**Severity:** Critical · **Status:** CONFIRMED
**File:** `app/api/blackjack/random/route.ts:32`, `:116`

The route's own docstring states: *"Once randomness is issued for a (landId, nonce), the same randomness is returned for all subsequent requests until the nonce is consumed onchain."* That holds for **105 seconds**.

```ts
const RANDOMNESS_LIFETIME_SECONDS = 60;
const ACTION_LOCK_TTL_SECONDS = RANDOMNESS_LIFETIME_SECONDS + 45;   // 105s
...
await redisCompareAndSetJSON(lockKey, null, serialized, ACTION_LOCK_TTL_SECONDS);
```

`isExpiredActionLock` also treats the lock as expired after 105s. Meanwhile the signature the contract verifies has **no expiry field** — the code says so itself:

```ts
// Current Solidity only verifies this legacy payload. The app/API lock also
// binds deal amount and API expiry until a future contract upgrade can do it onchain.
const messageHash = keccak256(encodePacked(
  ['uint256','uint256','bytes32','uint8','uint8','address'],
  [BigInt(landId), currentNonce, randomSeed, actionNum, handIndexNum, effectiveBettingToken]
));
```

**Attack:** request a deal seed → wait 105s → request again → receive a *new* valid seed for the same nonce. Old signatures remain redeemable forever. Accumulate N signatures, simulate all deals offline, submit the best. At ~105s per attempt that is ~34 candidate deals/hour against a house edge in the single-digit percent range.

**Fix (app-side, no contract change):** make the lock durable rather than TTL'd. The route already reads `blackjackGetNonce` — keep the lock until it observes the nonce advance. A long TTL (e.g. 24h) plus nonce-advance invalidation closes it.

### F086 — The signed blackjack payload omits the bet amount

**Severity:** Critical · **Status:** CONFIRMED
**File:** `app/api/blackjack/random/route.ts:589`

Bet size is enforced only by the same 105-second Redis lock; it is not in the signed message. A caller going directly to the contract can obtain a deal seed, compute the resulting cards, and *then* choose the stake.

**Fix:** the same durable-lock change as F085. With the lock persisted until nonce advance, the bet amount stays pinned for the life of the signature.

### F087 — The randomness endpoint is unauthenticated and trusts a body field as identity

**Severity:** Medium · **Status:** CONFIRMED
**File:** `app/api/blackjack/random/route.ts:415`

`playerAddress` arrives in the POST body with no session check:

```ts
const { landId, action, playerAddress, handIndex, bettingToken, betAmountWei } = body;
if (typeof playerAddress !== 'string' || !isAddress(playerAddress)) { ... }
```

Ownership is then verified *against that supplied address*. Since landIds and owners are public onchain, a third party can create the lock first — pinning a victim's nonce to an action and bet they did not choose — and burn their 30/min bucket. The victim gets *"Action locked. Retry the same Blackjack action and bet amount."*

**Fix:** require the chat session and derive `playerAddress` from it rather than from the body.

**Related (F088, PARTIAL):** the action lock is fail-open. During a sustained Redis outage the route falls back to a per-instance in-memory lock and can mint a second valid signature for the same nonce. Requires three consecutive Redis failures, so a single blip is not enough.

### F187 — Casino never checks reward-pool solvency

### F225 — Read timeouts are invisible to the RPC circuit breaker

**Severity:** Critical · **Status:** CONFIRMED
**File:** `lib/base-rpc.ts:507`

`isConnectivityError` does not match viem's timeout wording, and `eth_call` carries a blanket exemption. A provider that has degraded into pure timeouts keeps its health score, keeps its ranking, and keeps receiving traffic. The failover machinery never engages for the most common real-world failure mode.

**Fix:** classify viem's `TimeoutError` (and `AbortError`) as connectivity failures, and drop the `eth_call` exemption so timeouts feed health, ranking and the breaker like any other transport error.

**Related (F226, PARTIAL):** the server read cascade has no overall deadline (up to ~46s across 10 waves) while the browser abandons at 12s, so the tail is unbounded dead work. The code comment justifying the 12s client timeout is factually wrong, and round 2 replays the same failed endpoint order.

### F198 — SIWE domain and origin validated against client-influenceable headers

**Severity:** Critical · **Status:** CONFIRMED
**File:** `lib/chat-auth.ts:552`

The allowlist a SIWE message is checked against is derived from `X-Forwarded-Host` / `X-Forwarded-Proto`. Where an edge or proxy tier passes those through, a signature phished on an attacker-controlled domain can mint a chat/gamification session for the victim's address.

**Deployment caveat, verified:** on the current Vercel / `next start` shape those headers are **not** honoured for `nextUrl` — I tested `Host:`, `X-Forwarded-Host:` and `X-Forwarded-Proto:` spoofing against the production build and the origin allowlist held (403). So this is deployment-edge dependent rather than exploitable today. It is nonetheless one proxy configuration change away from failing open, and the control should not depend on that.

**Fix:** validate against a fixed server-side allowlist constant, never a request header. viem 2.56 also ships `parseSiweMessage` / `validateSiweMessage` / `verifySiweMessage`, which would replace the hand-rolled parsing here.

### F051 / F054 — The ticking deadline aborts monitoring of transactions that succeeded

**Severity:** High · **Status:** CONFIRMED
**File:** `components/transactions/transaction-kit.tsx:1983`, `:833`

A deadline recomputed every 60s changes the calls digest, which aborts the live monitor and **permanently suppresses `onSuccess` / `onStatus`** for a transaction that already landed.

Separately, the primary game button has **no chain gate and no wallet-readiness gate** — the chain half of the routing guard is dead code, and `submit()` can silently no-op.

This is the shared root of PX-05's stale panel and lost mission credit, and of F053's double charge.

**Fix:** exclude the deadline from the identity used to key the monitor; gate the button on chain id + wallet readiness with a visible reason when blocked.

**Related (F049, PARTIAL):** the atomic-bundle assertion treats a missing EIP-5792 `atomic` field as failure, which would strand an already-confirmed bundle in `transactionUnresolved`. Verification could not show a supported wallet that omits it, so severity is lower than originally claimed.

**Related (F017, PARTIAL):** a successful batch whose wallet reports no receipts spins for 30 minutes and never reconciles.

### F066 — Two Redis caches can never hit

**Severity:** High · **Status:** CONFIRMED
**Files:** `lib/stake-leaderboard-service.ts:156`, `lib/user-stats-service.ts:202`

`@upstash/redis` already deserializes JSON. The code parses it again, the comparison never matches, and the cache is a 100% miss. Every stake-leaderboard request rebuilds from chain; the 30-second user-stats cache is inert.

Compounding it: `/api/leaderboard/stake/warm` exists but is **scheduled nowhere** — no Vercel cron, no QStash config.

### F104 / F136 — Two flows can wedge permanently with no user-facing escape

### F199 — A Redis blip logs everyone out

### F089 — Smart-wallet users are asked to sign, then always rejected

**Severity:** Medium · **Status:** CONFIRMED
**File:** `app/api/spin/commit-state/route.ts:77`

Verification uses viem's EOA-only `verifyMessage`, so every Base Account / Coinbase Smart Wallet player is prompted after each spin commit and then 401'd.

**Related:** smart-account detection in `lib/smart-wallet-context.tsx` is bytecode-only, so counterfactual (undeployed) Base Accounts are misclassified as EOAs and lose gas sponsorship on their first transaction.

### F105 — All 18 bridge diagnostic routes are public under self-hosted deployments

**Severity:** Medium · **Status:** CONFIRMED
**File:** `lib/bridge-debug-access.ts:27`

```ts
function isLocalhostRequest(request: NextRequest): boolean {
  const hostname = request.nextUrl.hostname.toLowerCase();
  return hostname === 'localhost' || hostname === '127.0.0.1' || ...;
}
```

This keys on the server's **own bound host**, not the caller. On the production build served at `localhost:3100`, `/api/bridge/check-pools`, `debug-deep`, `trace-mint` and `verify-wsol` all returned 200 with full internals to an unauthenticated caller — including with `Host: evil.example`. Behind an nginx/Docker reverse proxy this is the normal deployment shape.

**Verified NOT exploitable on Vercel**, where the bound host is the deployment domain. The 30/min rate limit also works correctly (exactly 30 pass, then 429).

**Fix:** gate on `process.env.NODE_ENV !== 'production'` **plus** admin auth, rather than on a hostname the deployment topology controls.

### F152 — Aborting an AI stream bypasses the daily token budget

**Severity:** High · **Status:** CONFIRMED
**File:** `lib/ai-service.ts:2591`

`trackAIUsage` runs only on normal completion. A client that aborts — or receives an empty stream — skips both message persistence and accounting, so `AI_MAX_TOKENS_PER_DAY` and the per-address message cap are not enforced for those requests. An unbounded spend path against a paid provider key.

**Fix:** record usage in `onFinish` **and** in an abort/error handler, or reserve budget up front and settle afterwards.

## 9. Appendix — reproduction harness

**Running the app for runtime testing**

Use the **Local Test Wallet** surface: `http://localhost:3000/?surface=test`, or click "Local Test Wallet" on the login screen. It is gated to localhost + non-production by `isLocalTestAuthAllowed()` and uses the key in `.env` (`NEXT_PUBLIC_LOCAL_TEST_WALLET_*`).

> **Warning:** that wallet is on **Base mainnet**. Transactions are real and cost real gas.

**Producing a production build without killing the dev server**

```bash
git worktree add --detach <tmp> HEAD
robocopy node_modules <tmp>/node_modules /E /MT:16    # exit code 1 == success
cp .env <tmp>/.env
cd <tmp> && ./node_modules/.bin/next build && ./node_modules/.bin/next start -p 3100
```

A `mklink /J` junction for `node_modules` does **not** work — Turbopack aborts with *"Symlink [project]/node_modules is invalid, it points out of the filesystem root"*. Do not use `npx next build` in the worktree either; npx fetches its own Next and fails on missing react.

**Verifying onchain**

viem scripts must live **inside the repo root** to resolve `node_modules`, and must be `.mts` (top-level `await` fails under tsx's CJS transform). The RPC key in `.env` is `RPC_NODE`. Delete scratch scripts afterwards.

**Profiling caveat**

A client-side `window.fetch` counter under-reports, because `components/efp-transaction-boundary.tsx` monkey-patches `window.fetch` globally. Use the dev server's own request log as ground truth.
