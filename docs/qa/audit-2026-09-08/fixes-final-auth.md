# Final auth closure — repeated disconnect and late wallet completion

## Revalidation and causal evidence

The medium real-app ledger contained one desktop journey that stayed connected after its second Disconnect Wallet action. Its immediate rerun passed. The earlier record did not establish the exact scheduling trigger, and this follow-up does not relabel that individual run as proven HMR behavior.

Controlled tests using the installed, real Wagmi provider, connection store, connect/reconnect actions and mutation hooks reproduced two defects in the unchanged cleanup implementation:

1. `WalletProfile` passed Wagmi's fire-and-forget `disconnect()` mutation into `disconnectWalletIdentity`. The helper accepted `() => void`, invoked it without awaiting completion, cleared identity and released the reconnect lock. With the synthetic connector's disconnect held, the UI reported success and cleanup became idle while the actual connector remained connected. The corrected expectation failed in `output/auth-disconnect-before-valid/auth-disconnect-final-disc-c5de9-cess-or-releasing-reconnect-1440-light`.
2. Both production Wagmi providers relied on default `reconnectOnMount=true`. After a successful connector disconnect, remounting that provider while the remote session DELETE was held reconnected the still-authorized connector. The cleanup lock governed app login actions but did not govern SDK hydration. The corrected expectation failed in `output/auth-disconnect-before-valid/auth-disconnect-final-a-pr-92f60-nnect-the-signed-out-wallet-1440-light`.

A further queued-reconnect probe established why checking only the visible account status is insufficient: a reconnect started before logout can resolve afterward and restore Wagmi's connection inventory while its account status remains `disconnected`. That leaves an invisible active connection which can block the next explicit connect. The inventory expectation failed in `output/auth-disconnect-queued-before/auth-disconnect-final-a-qu-036c7-ve-connection-after-cleanup-1440-light` before the final guard was changed to inspect `useConnections()`.

Independent review also reproduced two remaining boundaries (`output/auth-review`): an unresolved SDK logout/disconnect kept every sign-in action pending indefinitely; and a held SDK reconnect for owner A could overwrite a newer explicit Mini App connection for B, both with a continuously mounted provider and after a remount. The latter occurred after reconnect had been explicitly allowed again, so the signed-out inventory guard alone could not reject A. These were fixed before final closure.

These are demonstrated mechanisms for losing sign-out intent. The original one-off journey has no private trace or exact remount timeline, so its precise trigger remains unproven.

## Fix

- Cleanup requires and awaits the SDK disconnect promise. WalletProfile, surface switching, Base auth failure cleanup and Privy reset use `disconnectAsync`, rather than `mutate()`. Rejected disconnects still clear local app identity and bounded remote session state, then report failure; they cannot display successful sign-out. A failed previous-wallet logout also prevents switching to a new auth surface.
- The synchronous auth cleanup store retains sign-out intent after cleanup finishes. Automatic reconnect stays suppressed for the current document. After any cleanup generation, explicit Mini App reconnect now establishes a fresh document before connecting, matching the isolation already used for web surface changes. Old SDK promises therefore cannot mutate B's new connection. Normal initial-load restoration and first-document retry remain enabled.
- `SessionWagmiProvider` supplies the same reconnect policy to Core and Privy providers. Its guard retires late connections from the SDK's actual connection inventory, including records hidden by a disconnected account status. It captures the responsible connector, serializes cleanup and attempts each failed connection record once, avoiding an automatic retry loop.
- Player connection state and auth attempt validity also respect sign-out intent. A late SDK connection cannot reopen the game while its cleanup is being retired. Existing owner/surface/generation checks continue to fence signatures, session POST publication, errors and finalizers. Automatic Mini App connection and Privy address hydration respect the retained intent.
- At 15 seconds, unresolved SDK cleanup exposes an accessible Reload app safely action while leaving reconnect fenced. Recovery clears only auth state, performs bounded remote session cleanup and reloads with a signed-out URL marker. A separate recovery lease keeps the old document fenced even if its original SDK promise finishes during this process. The marker suppresses reconnect during first client hydration; a subsequent explicit Mini App or web sign-in clears it. Tests verify that this does not create a permanent logout loop.
- The existing auth-only cache selection and durable transaction/preference protections are unchanged. No broad cache purge, transaction recovery change or financial send was introduced.

## Limits and public observations

The controlled connector proves orchestration behavior; it does not emulate every vendor's native logout sheet or physical Mini App host. An SDK logout/disconnect promise that never settles remains fenced, but now has bounded stalled-state feedback and explicit fresh-document recovery. Remote session DELETE remains bounded at ten seconds. The tradeoff is one page reload for explicit Mini App reconnect after cleanup; normal initial connection and first-document retry do not reload. No physical-device completion claim is made.

The otherwise-passing real local-wallet journeys still recorded an `Unexpected SIWE domain` response. Read-only verification confirms that `getExpectedBaseUrls()` trusts only configured `NEXT_PUBLIC_URL`, while the browser signs `window.location.host/origin`. Running the development app with public `NEXT_PUBLIC_URL=http://localhost:<port>` and matching `PIXOTCHI_APP_TEST_URL` is the legitimate aligned-origin acceptance setup; request headers are not added to the trust boundary. No environment secrets were read and validation was not loosened. Root owns that server configuration and final integration evidence.
