## SS-25 — Shared responsibilities and explicit ownership

The duplication and ownership problems still existed after the medium round. Verify Claim's parent capability gate was already corrected; it was revalidated without adding another gate. The medium round had also supplied shared owner-operation scopes, claim recovery presentation, typed history/activity parsing, Activity feed/view hooks and ranking read-readiness contracts. This round builds on those contracts.

| Before | After | Why |
| --- | --- | --- |
| Public and AI independently finished a shared scalar sending state. | `useChatSending` owns one identity and AbortSignal per mode. Finishing or cancelling one mode does not unlock the other. Credential waits settle immediately on cancellation, and their later results cannot dispatch a question. | Desktop supports two active composers; each requires an independent operation lifecycle. |
| Header, composer and message consumers subscribed to the same changing context object. | Separate header, controls, session, per-mode pane and per-mode composer contexts. The desktop pane shell and typing indicator use the composer contract; streamed message arrays stay in message consumers. | AI chunks no longer invalidate the header, Public pane or AI composer. A compatibility context remains for existing consumers and test harnesses. |
| History request controllers and principal checks were distributed within the provider. | `useChatHistoryRequests` owns principal/request identity, abort and completion. A newer AI send invalidates its earlier history; an accepted Public POST invalidates an earlier Public read and explicitly releases that read's gate/loading. | Late snapshots cannot erase newer messages, including after A→B→A wallet changes. |
| Polling/history effect cleanup could abort an unrelated Public POST when AI established its conversation ID. A server echo plus optimistic message could become duplicate accepted rows. | History subscription cleanup owns only the subscription. Public send cancellation belongs to explicit cancel, chat close or principal/unmount lifecycle. POST reconciliation removes both the optimistic ID and any already-received accepted ID before inserting the accepted message. | Request timing does not cancel or duplicate a player's accepted message. |
| Mint-share and its public share page each maintained strain/art mappings. Activity had separate item/building icon tables. | Both share consumers use `PLANT_ART_MAP`; Activity consumes canonical item icons and building helpers through typed `activity-metadata`. Historic Fence identity, SpinLeaf naming and signed reward formatting are explicit. | Art and resource identity changes have one canonical source. Unknown/degraded rewards remain unavailable instead of becoming fabricated values. |
| Mobile/desktop plant filters and compact/full revive controls repeated the same logic. | One `RankingPlantFilters` owns selection transitions, one `RankingPlantSummary` owns plant identity/metrics, and one revive button branch serves both row presentations. | Responsive markup cannot drift in filter behavior or revive readiness. Existing transaction preflights remain unchanged. |
| Activity rows and ChatMessages maintained separate relative-time intervals. | They share `useRelativeTimeTick`, which runs one interval for mounted subscribers, pauses when the document is hidden and refreshes on visibility restoration. | Relative-time updates have one lifecycle; feature-specific data fetching remains explicit. |
| Hidden Airdrop still mounted eligibility effects. | A parent capability wrapper returns before mounting `AirdropClaimContent`; the already-correct Verify Claim parent gate is retained. | Disabled capabilities issue no eligibility reads. |
| Streamdown's custom memo comparator ignored exported props other than text/animation state. | Default shallow React memo comparison covers all props, with stable default plugin configuration. | Changing classes or Markdown renderers with unchanged text is applied. |
| Embedded-wallet export kept Wallet Profile open but used the default dialog layer. | Export uses the shared `layer="nested"` contract. | Its overlay sits above its parent; Escape closes the child and restores the export opener. Authentication teardown remains owned by the authentication changes. |

Evidence: `tests/frontend/social-low.spec.ts` mounts the production ChatProvider, real installed AI SDK, real composer, MessageResponse/Streamdown, claim wrappers, ranking components and WalletProfile. The transport/credential boundaries are controlled. The tests cover overlapping sends in both completion orders, separate send locks, failed draft preservation, actual incremental streaming and a newly created conversation ID, composer/header commit counts, older Public GET completion after acceptance, accepted echo reconciliation, Stop during delayed credentials, zero hidden capability reads, changed Markdown props, filter transitions and nested-dialog close/focus.

## Final settled Activity correction — SS-25 / FND-V6

A later settled real-app review exposed `Plant #undefined` beneath BoxGame records. The earlier controlled fixtures always supplied `nftId`, so they did not cover the public GraphQL projection that produced those records. The public query omitted `nftId` for **Played, ItemConsumed and ShopItemPurchased**; the corresponding personal-feed queries included it. The server passes those indexed arrays through to Activity, while the new concise source line unconditionally stringified the absent field. The omission also allowed same-name, same-time Played records from distinct plants to share the existing deduplication key.

The deployed contract ABI records the Played plant as an indexed integer ID, and the personal indexer query/DTO uses `nftId`. The initial public API read confirmed 43 Played, 90 ItemConsumed and one ShopItemPurchased record missing that field. Counts changed as new events arrived. A direct configured upstream schema request returned 404; no schema introspection success is claimed. The actual local API and settled app later confirmed the corrected query projection.

| Before | After | Why |
| --- | --- | --- |
| The three public plant-origin query selections omitted `nftId`. | All three select `nftId`, matching the personal feed. Existing same-plant/richer-reward deduplication remains unchanged. | Actual identity is available for context and deduplication. Same-name records from different plants remain distinct. |
| Absent, malformed and unsafe-number IDs could be stringified as asset context. | One identity reader accepts nonnegative integer IDs, including zero and large decimal strings, and returns explicit absence otherwise. Summaries use an available name or omit the source portion; expanded plant/land details use neutral wording. | No IDs are guessed from names, and absent identity never grants an ownership marker. All six plant-origin variants and the landId/tokenId/attackerLandId paths are exercised. |
| Two missing Attack IDs compared equal and could manufacture a win. | Shared outcome interpretation returns unavailable when attacker or winner identity is missing/malformed. Headline, icon and expanded narrative are neutral. | Valid wins/losses and personal perspective are preserved; malformed identity is not a game result. |
