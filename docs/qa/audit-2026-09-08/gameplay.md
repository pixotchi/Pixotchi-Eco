# Gameplay frontend audit — 8 September 2026

This is a read-only audit of the current source, not an old audit summary. It covers the complete Plants/Lands presentation and care, rename, profile, map, image and timer components listed below. Building panel details are in `building-panels.md`. A bounded live browser follow-up is documented at the end, with 21 screenshots at 320/390/1440px. Findings distinguish source-confirmed behavior from reproduced visual issues and untested runtime branches. No transactions were submitted by this audit worker and no app code was changed. Apple-design skill criteria informed the review: clear feedback, predictable state, touch usability, typographic hierarchy, interruptible movement and accessibility.

## What this part of the app does

The Farm tab switches between owned plants and owned lands. `DashboardTab` uses React Activity to preserve each view's local state and lazily mounts Lands on its first visit. Plants uses an EVM wallet or Solana twin address, and an owner-scoped React Query list. The selected plant is derived from the current list by ID. A plant stage displays points, stars, remaining life, health and active fences; players can rename it, claim ETH rewards while burning points/resetting the level, open the arcade, buy immediate care/protection or revive a dead plant.

Care combines garden items and protective shop items, grouped by effect. Every tile opens a common review dialog/mobile sheet. Review routes among EVM SEED allowance plus purchase, smart-wallet multi-item bundles, ETH swap-plus-buy and Solana bridge variants. Fence duration has contract bounds, remaining-lifetime bounds and a separate quote. This is a complex transaction surface, not a static catalog.

Lands is EVM-only. It derives selection from the owner list but loads a selected land's village, town, Barracks and Casino building state imperatively. Land IDs and selected building/type persist in local storage. Village/town choices drive layered scene artwork and an inline detail panel. Desktop exposes both grids simultaneously; mobile/tablet expose a Village/Town toggle. Cross-land batch claim and batch quest tiles share the grid with actual buildings. The map renders a procedural tile world in canvas, with drag/pinch, keyboard panning, owner lookup and nested player profiles. Building panels consume land resources, approvals and a shared chain block clock.

## Highest-impact findings

### G01 — P1: Fence-only restrictions silently block ordinary plant care

**Source-confirmed.** `components/item-details-panel.tsx:149-167` computes `fenceV2BlockedByV1` and `fenceV2Bounds.todCapBreached` for every selected plant. The common SEED approval action at `:697-704` disables for both flags without checking `isFenceItem`. Consequently, a plant with less than the minimum one-day lifetime, or an active V1 fence, cannot approve/buy an ordinary garden care item through this branch. This is precisely when buying lifetime can be urgent. Its user-facing disabled reason at `:286-301` only mentions those conditions for fence items, so the player receives no explanation for the disabled normal-purchase button.

**Fix:** derive a typed purchase readiness result by item kind; apply fence restrictions only to fence purchases. Keep the visible disabled reason and action readiness derived from the same result. Validate garden purchase with low lifetime, V1 fence, no allowance, smart wallet and regular wallet; then validate fence purchase still observes its bounds.

### G02 — P1: Plant rename changes payment path while an ETH quote is loading or unavailable

**Source-confirmed.** `components/edit-plant-name.tsx:210-242` loads a quote and sets it to null on failure. Rendering chooses ETH only when the quote exists and is no longer loading (`:352-381`); all other cases fall through to SEED balance/allowance or the SEED action (`:382-420`). `canAffordNameChange` also falls back to SEED without a quote (`:187-189`). An ETH-mode player can therefore see an enabled SEED approval/rename while ETH is loading or after its quote fails. The care component already models ETH quote failure explicitly, so this is inconsistent as well as surprising.

**Fix:** choose the intended payment asset before loading any quotes; keep an exclusive ETH branch with loading/error/retry states. Do not switch payment asset implicitly. Reuse `useSeedPurchaseQuote` and a common payment readiness model rather than another rename-specific quote effect.

### G03 — P1: Submitting a land rename unmounts its own transaction controller

**Source-confirmed lifecycle break; precise wallet timing needs live reproduction.** `components/edit-land-name.tsx:69` defines `canSubmit = isNameValid && !isTransactionPending`; `:90` sets pending on button click; `:132-147` mounts `LandNameTransaction` only while `canSubmit` is true and substitutes a plain disabled button otherwise. `components/transactions/land-name-transaction.tsx` forwards that click to GameTransaction, which passes it to TransactionButton (`components/transactions/game-transaction.tsx:215`). Thus the first click causes the feature's transaction component/status host to unmount during the action. The transaction audit verified that controller cleanup marks it unmounted and unregisters recovery, while error/status handling can skip an unmounted controller. Durable transaction recovery may still preserve a transaction result; it does not preserve this rename dialog's local flow.

**Fix:** keep the transaction component mounted for the full operation and use its disabled/pending state. Derive the action label from validation before submission and from transaction status afterwards. Test both a wallet rejection and successful confirmation without closing/reopening the dialog.

### G04 — P2: A land switch temporarily displays and allows selecting the previous land's buildings

**Source-confirmed stale presentation.** Starting the new fetch only sets `buildingsLoading` (`components/tabs/lands-view.tsx:524-542`); land-switch handling resets `selectedBuilding` but leaves both building arrays in place (`:855-880`). The grid only shows loading when both arrays are empty (`:1142`), and its buttons remain enabled (`components/building-grid.tsx:56-82`). The new land's scene also consumes those retained arrays (`lands-view.tsx:1050-1055`). A player can see old levels/artwork and click an old building object, which is then passed alongside the new `landId` to details (`:1266-1279`). Request-generation guards prevent an old network response from winning, but do not prevent this display mismatch while the new request runs.

**Fix:** key the building resource by owner + land ID, derive selection by building ID from that matching resource and gate actionable data on identity. Preserve old content only when refreshing the same land, with a subtle refreshing state. Reproduce with two lands with different levels and throttled RPC.

### G05 — P2: Plant-care catalog failure/loading is rendered as a blank card

**Source-confirmed.** `useItemCatalogs` exposes the query state but defaults missing lists to `[]` (`hooks/useItemCatalogs.ts:29-33`). Plants only takes the two arrays (`components/tabs/plants-view.tsx:134`). `PlantCareCatalog` only renders nonempty groups (`components/plant-care-catalog.tsx:30-54`), so a first load or failed catalog read leaves a Plant care heading and empty space, with no loader, explanation or retry. Because the two catalog calls use `Promise.all` (`useItemCatalogs.ts:20-23`), a failure in either also removes the other on a first read.

**Fix:** pass resource status/retry explicitly, preserve successful catalog parts, use a catalog-shaped skeleton and distinguish no available items from unavailable data. Do not block the plant stage on catalog loading.

### G06 — P2: Several essential read failures have no honest state or recovery action

**Source-confirmed.** Fence quote failure produces “Fence quote unavailable. Retry to continue.” (`components/item-details-panel.tsx:295`) but the SEED branch only renders `DisabledTransaction` (`:662-666`); there is no fence-quote retry control. Retry is implemented only for ETH quotes and SEED balances. Fence config failure is console-only (`:127-146`) and the UI assumes duration bounds 1–30 days while config is absent (`:160-167`). Revive price/balance reads use `Promise.allSettled` but ignore rejected price/balance results (`components/tabs/plants-view.tsx:270-290`), leaving a default 100 SEED price or previous/zero balance as if known (`:777-788`). Revive allowance failure disables its button without a retry (`:807-812`). Plant-rename allowance errors similarly have no in-dialog retry (`components/edit-plant-name.tsx:382-391`), and price failure silently becomes the 350 SEED fallback (`:143-153`). Land allowance fetch failures become zero allowance (`lands-view.tsx:426-435`), which downstream reads as “needs approval”.

**Fix:** use a shared `unknown/loading/ready/error` resource model for price, balance, allowance and config. Money/config errors should preserve last-known values only as explicitly stale data and keep dependent actions gated. Put “Retry” beside the precise failing resource and make promise results owner/action scoped. Avoid instructing retry where none exists.

### G07 — P2: Mobile building browsing hides the result of a selection below the grid

**Source-confirmed flow; exact scroll depth is device-dependent.** Below desktop, the layout is a single column (`components/tabs/lands-view.tsx:1139`); the whole building grid precedes the detail panel (`:1141-1281`). Selecting a tile just updates React state (`:907-910`) and leaves scroll/focus unchanged. There is no dialog, detail anchor, live announcement or focus transfer. A phone player can tap a town tile while its selected action appears well below the viewport. Care uses a review sheet for the same catalog-to-detail task, so behavior differs across the two main Farm areas.

**Fix:** mobile building selection should open an accessible detail sheet, or an inline detail region with deliberate reveal/focus and a clear return path. Preserve a side panel on sufficiently wide layouts. Keep button selected-state feedback immediate in either presentation.

### G08 — P2: Mobile building grid has no small-container layout and truncates important labels

**Visually reproduced at 320×568; not a page-level horizontal-overflow bug.** Default grid is four columns with 16px gaps (`components/building-grid.tsx:150`); each icon is a 64px inner box inside a bordered button (`:61-64`), requiring approximately 312px of interior width before any card padding. `Card` adds 16px per side (`components/ui/card.tsx:16`). At 320px, rendered button x positions were 21.25, 91.75, 162.25 and 232.75, each 66px wide: only 4.5px remains between icons, and labels grow beyond their nominal tracks. Solar Panels/Soil Factory visually run together; Stake House/Warehouse/Marketplace run together in Town. `document.documentElement.scrollWidth` remained 320px, so this is cramped/overlapping content inside the layout rather than horizontal page scrolling. The issue was not present at 390px or 1440px in the same state. The mobile branch does not enable dense/wrapping labels (`building-grid.tsx:88-97`), while wide desktop deliberately wraps them (`lands-view.tsx:1199-1200`). Evidence: `320-village-grid.png`, `320-town-grid.png`, with `390-town-grid.png` and `1440-village-production.png` as comparisons.

**Fix:** use container queries with three columns when necessary; make the whole tile (icon + wrapping label + status) interactive; establish a common minimum tile width and consistent label block. Verify 320, 360, 390 and 430px widths, browser text zoom and maximum level/status values.

### G09 — P2: The map invents a supply number when the real read fails

**Source-confirmed.** `hooks/useLandMap.ts:39-49` returns `Math.max(500, maxUserTokenId)` on supply failure, or 0 while loading. `lands-view.tsx:386` ignores the hook's loading flag. The modal presents that number as “Plots Discovered” (`components/map/land-map-modal.tsx:239-240`), and uses it as a minted/unminted threshold (`:166`; `components/map/land-map-canvas.tsx:19-20`). The map therefore changes what land appears owned/available based on a guessed fallback and gives no indication the count is unknown. Missing neighbor metadata and owner lookup failures are also indistinguishable from normal fallback names/“Unknown” (`land-map-modal.tsx:195-202`, `:218`, `:379`, `:414`).

**Fix:** separate known minted IDs/supply from a rendering extent. Show “Map data unavailable” with retry and the last verified count if available. Render known owned lands from the ownership list regardless of supply status, and use an unknown state for other plots until verified.

### G10 — P2: Map image fallback can throw instead of falling back

**Source-confirmed broken-image path; browser failure injection recommended.** The sprite loader resolves a truthy `HTMLImageElement` even on `onerror` (`components/map/land-map-canvas.tsx:96-102`). Drawing only checks whether that object exists (`:266-267`, `:293-294`, `:301-302`, `:309-310`, `:317-318`, `:343-344`, `:351-352`, `:359-360`). A broken image is therefore sent to canvas `drawImage`, whose invalid-image path can throw; the intended colored fallbacks only apply to null objects. The load-level catch cannot catch a later render-effect error.

**Fix:** resolve failed assets to null/a tagged failure, validate `complete && naturalWidth > 0` before drawing, and use the existing colored fallback. Add a canvas-level recoverable fallback if a drawing error still occurs. Test with one sprite request failed, not only all assets cached.

### G11 — P2: Profile stats advertise interaction they do not implement; network errors disappear

**Source-confirmed.** Follower and following counters have `cursor-pointer` plus hover opacity but neither an event handler nor a link (`components/plant-profile-dialog.tsx:631-639`). Owner stats fetch game stats and stake together (`:126-142`); errors are not read and the entire owner stat set becomes null (`:557-573`). EFP query errors are displayed as “No social data available” (`:145-153`, `:641-643`) without retry. These are distinct states: a player having no followers and the app failing to load followers should not look the same.

**Fix:** either implement accessible buttons/links to relationship lists or remove the interaction styling. Render each stats group with its own loading/error/retry state. Use shared profile data hooks rather than EFP mission/network orchestration inside this 675-line dialog.

### G12 — P2: Pure Solana users cannot reach the implemented rename bridge

**Source-confirmed branch mismatch.** Plants derives an owner from EVM address or Solana twin address (`components/tabs/plants-view.tsx:118-128`). `EditPlantName` determines ownership from only `useAccount().address` (`components/edit-plant-name.tsx:71`, `:105-106`) and returns null when that EVM address is absent (`:266-268`). Yet it implements a Solana bridge rename branch (`:329-351`). A pure Solana login can view its twin-owned plant but gets no rename trigger.

**Fix:** use the same effective-owner abstraction across view and action components; separate “can display this ownership action” from the chain/account used to submit. If rename is intentionally unsupported, show a clear supported-capability rule and remove unreachable bridge code.

## Maintainability seams causing these defects

- **Payment/readiness logic is repeatedly reimplemented.** Care, revival and rename each have their own allowance shape, fallback policy and quote branches. The resulting behavior is already divergent (G01, G02, G06). Introduce feature hooks that return one discriminated readiness state and a typed transaction intent, while sharing resource semantics and payment display.
- **Building resource orchestration is in a 1,305-line view.** `lands-view.tsx:85-117,388-714` implements request identities, generation counters, pending/queued requests and arrays beside JSX. Owner lists already use React Query. A transient selected ID is a valid query key; selected-land building queries can also use the existing query infrastructure with owner + land identity, reducing the stale-grid seam in G04.
- **The same tile is manually mirrored.** `UtilityBuildingTile` explicitly mirrors BuildingItem (`lands-view.tsx:170-228` versus `building-grid.tsx:27-107`), including strings of utility classes. Extract a shared tile shell with icon, title, subtitle, status and selection affordances. Keep utility actions semantically distinct from constructed buildings despite common visuals.
- **Desktop/mobile copies need continual synchronized edits.** `lands-view.tsx:1148-1244` repeats grids and utility tile configuration for responsive branches. Define one area/utility model and render it through a small responsive presentation component rather than copy labels and callbacks three times.
- **Transaction side effects are repeated by payment route.** Care's `handlePurchaseSuccess` (`item-details-panel.tsx:369-403`) coexists with multiple independently copied mission payload/retry implementations (`:730-790`) and routes that only call `onPurchaseSuccess` (`:592-595,614-617,716-718`). Whether every path is backed by transaction-level mission ingestion is outside this worker's scope; duplicated policy makes route behavior hard to reason about. Consolidate verified purchase completion handling.
- **Presentation, identity and social transaction machinery share one profile component.** `plant-profile-dialog.tsx` spends ~400 lines on EFP workflow/mission state before its layout. Extract shared owner statistics and relationship workflow hooks; keep a presentational profile shell with honest resource states.
- **Scene metadata is derived from display names.** Land layer mapping (`LandImage.tsx:20-28,53-57`), building metadata and care kind detection depend on labels. Use stable IDs and explicit metadata so copy changes do not change behavior or remove artwork.
- **Primitive props can be misleading or stale.** `BuildingGridProps.currentBlock` is required but never consumed (`building-grid.tsx:20,113-122`); callback wrappers add little (`:123-125`). `PlantImage` width-responsive `sizes` logic is applied to SVG-only assets (`PlantImage.tsx:119,123-127,141-143`). Remove unused seams as part of extraction, not as a cosmetic rewrite.

4. Payment fixtures: EVM regular, smart wallet SEED mode, smart wallet ETH mode, pure Solana twin; no allowance/insufficient/exact balance; failed/stale quote; wallet rejection and confirmation. Assert the reviewed asset, price, plant/land and target match the submitted intent.

6. Profile: long ENS/Basename, no plant, owner stats failure, EFP failure, self/other/no account, pending relationship update; ensure all interactive-looking regions act and focus returns to their source.
