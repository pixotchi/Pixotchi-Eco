# Pixotchi frontend and player experience audit — 8 September 2026

Audited checkout `2d21280`, application version **1.8.35**. This is an assessment and proposed remediation plan. Application source was not changed. The existing `.gitignore` modification was present before the audit.

## Assessment

Pixotchi has a recognizable identity, substantial game depth, and a stronger frontend foundation than its remaining defects suggest. Shared controls, amount parsing, responsive dialogs, transaction reconciliation, ownership guards, semantic radio controls, and regression fixtures already exist. Preserve them.

The main problem is **inconsistent application of those foundations at feature boundaries**. A validated amount primitive coexists with a staking render that throws on an intermediate decimal. A durable transfer plan coexists with a confirmation screen reading a different selection. An amount-keyed quote hook exists, but minting still has a separate stale-quote window. Some consumers distinguish failed reads from zero; others invite actions using fallback values. Several large components own both money/game state and layout, making these divergences easy to introduce.

The visual issue is mostly hierarchy and adaptation: many nested blue surfaces receive similar borders, gradients, rounding and emphasis; small metadata and oversized amount/illustration areas compete; tablet layouts remain phone-width; and secondary or promotional content sometimes precedes the player's primary task. The strongest direction is a calmer, clearer game interface that keeps the pixel art while making actions, amounts, state and recovery predictable.

**This audit establishes a complete mechanical source census within the specified folders, detailed domain source review, and broad runtime sampling. It does not certify 100% runtime UI/state/device coverage.** Some states require specific holdings, contracts, wallet types, host SDKs, failure injection or physical devices. Those gaps are recorded rather than counted as passing.

## What the application does and how it works

Pixotchi is a plant-care and land-management game on Base, available on the web and through Farcaster/Base Mini App environments, with an optional Solana identity/bridge path.

| Player area | Core behavior |
| --- | --- |
| Plants | Mint strains, maintain lifetime, increase points/level, buy care items and fences, collect ETH rewards, rename, revive, attack, collect stars and play arcade games. |
| Lands | Select land, inspect the map, upgrade production buildings, collect PTS/lifetime into a warehouse, apply resources to plants, run quests, stake, trade, train troops and raid. |
| Economy | SEED/LEAF/PIXOTCHI/ETH balances, token approvals, swaps, bundled purchases, staking, marketplace orders and NFT transfers. PTS, lifetime and stars are separate game resources. |
| Games | Box and star games, SpinLeaf, Roulette, Blackjack and Baccarat. Some require a later reveal/open action; pending identity and deadlines matter as much as the initial wager. |
| Community/progression | Activity, five current ranking selections including Rocks, Farmer's Tasks, public chat, read-only Neural Seed, profiles, EFP actions, tutorials, verification and airdrop claims. |
| Supporting routes | Status, mint sharing, feedback, broadcasts, updates, secret-garden interaction, error/404 recovery and administration. |

The [game shell](C:/Users/Goat/Documents/Pixotchi-Eco/app/(game)/page.tsx) owns Farm, Mint, Activity, Ranking, Swap and About. It dynamically loads visited tabs and uses React Activity to preserve mounted tab state while hidden. Query parameters and contexts track navigation; layout changes between bottom tabs and a desktop rail.

[Providers](C:/Users/Goat/Documents/Pixotchi-Eco/app/providers.tsx) route authentication, host detection, Wagmi/Privy, smart wallet/paymaster state, Solana support, balances, theme, effects, tutorials and chat. UI data comes from contract reads, React Query, same-origin APIs, indexer-backed feeds and Redis-backed services. These have different failure and freshness characteristics. The [transaction kit](C:/Users/Goat/Documents/Pixotchi-Eco/components/transactions/transaction-kit.tsx) handles submission, wallet execution, pending proof, recovery, receipt confirmation and resource refresh; feature adapters build calls and interpret game outcomes.

The key frontend invariants should be: every display/action belongs to the current wallet and asset; every quote belongs to its current inputs; an unknown value is never a zero; a confirmed transaction is distinct from a recovered result; and changing presentation never destroys the controller responsible for an active action.

For touch sizing, the proposed comfortable house standard is 44px; that is **not** a claim that every 32px control fails WCAG. WCAG 2.2's minimum target criterion is 24×24 CSS pixels with exceptions, including spacing. [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). Apple's guidance supports deliberate touch targets, legibility and adaptable layouts; it does not require replacing the game's identity with a generic glass interface. [Apple UI design guidance](https://developer.apple.com/design/tips/), [Apple accessibility guidance](https://developer.apple.com/design/human-interface-guidelines/accessibility/).

## Maintainability: consolidate the rules that already drift

The right unit of reuse is a repeated behavior with the same invariant, not every pair of visually similar components.

| Drift / duplication | Recommended ownership |
| --- | --- |
| Manual quote effects in mint/rename beside a stronger shared quote hook | One quote controller with input identity, cancellation, freshness, error and retry; feature adapters supply pricing intent. |
| Local balance/allowance flags that disagree about checking, error and shortage | One purchase eligibility model used by the review, CTA, transaction controller and retry. |
| Multiple active/result game states and receipt decoding fallbacks | A typed round identity/result model; retain game-specific rules and presentation. Unknown/recovered/expired are first-class states. |
| Desktop/mobile render branches coupled to transaction owners | Stable controllers above responsive presentation; use CSS/container layouts for relocation. |
| Plant/land/target pickers, repeated metadata and name validation layouts | Shared semantic asset picker, metadata row and rename form; preserve distinct domain validation/actions. |
| Number/time/status wording and repeated token metadata fallback | Authoritative resource formatting and content vocabulary, with explicit readiness instead of a plausible default. |
| Sliding indicator geometry and keyboard plumbing in tabs/radios | Share measurement/motion machinery; keep different ARIA and interaction semantics. |
| Theme arrays, browser-chrome colors and logo implementations | One theme definition/metadata source; one decorative logo implementation with variants. |
| Large global CSS and feature-local escape hatches | Surface/type/spacing tokens globally; feature geometry in owned styles; remove substring selectors and inert props. |
| `UntypedValue = any` used across many boundaries | Parse external data into domain types at entry points. Prioritize transaction/receipt/quote/game data before broad cosmetic typing work. |

The largest controllers include administration, transaction-kit, chat, swap, Blackjack and ranking. Their size is a maintenance indicator, not a bug by itself. Extract data adapters, eligibility, lifecycle and semantic view compositions in small verified changes. A wholesale rewrite would make the existing recovery behavior harder to preserve.

## Proposed delivery sequence

1. **Correctness pass:** staking crash, transfer review snapshot, ordinary-care fence guard, quote/payment identity, preflight/retry cleanup, stable transaction owners and accurate game outcomes. Add a focused real-component regression for each.
2. **Readiness/recovery pass:** uniform resource states, owner/land/token request fencing, quest/reveal deadlines, reachable marketplace orders, batch reconciliation and AI draft handling. Test failed/late/out-of-order reads and reopen/resume.
3. **Shared interaction pass:** mode-safe focus, contrast pairs, viewport-bounded menus, input parity, exact-amount inspection and a touch-efficient stepper. Verify keyboard, 200% text, all themes and performance/reduced-motion settings.
4. **Layout/hierarchy pass:** fluid tablet shell, compact mint/swap flows, building selection visibility, readable rankings/activity, consistent dialog headings/body/footer spacing, and useful empty-state actions. Review screenshots before merging each family.
5. **Maintainability pass:** extract the repeated controllers/rules above while preserving behavior. Retire duplicated paths only when their consumers and tests have migrated.
6. **Release verification:** actual app journeys using owned state fixtures/test contracts and real host/wallet/device checks. The fixture suite remains valuable, but passing it cannot certify these full flows.

Suggested shared spacing roles are 4/8px within compact icon/label groups, 12px within a control group, 16px between related sections and 24px between major tasks. These are proposed starting values, not an instruction to replace every existing gap mechanically. Give headings one consistent baseline and use line-height/wrapping tests before tightening cards.
